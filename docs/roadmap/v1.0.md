# Road to v1.0 — reached

**Lithair 1.0.0 shipped on 2026-06-30.** All eight gates below are resolved;
this document is the record of what 1.0 required and how each gate was met (see
the dated **RESOLVED** note under each). The stability contract it defines is
now in effect — see [`api-stability.md`](../reference/api-stability.md).

It was written pre-1.0, when — under [SemVer](https://semver.org/) — any minor
could break and there was no *contract* yet, to define what the v1.0 contract
would be and what had to be true before it was offered. The gates were green
before 1.0 shipped, not a quarter's end (Lithair has a solo maintainer).

## What "stable" means at 1.0

Three distinct compatibility surfaces, with different promises:

1. **On-disk event-store format** — the strongest promise. Data outlives
   binaries: any 1.x binary MUST replay an event store written by any
   earlier 1.x binary (`events.raftlog`, `state.raftsnap`,
   `events.raftidx`, `meta.raftmeta`, both JSON and binary log modes).
   Breaking the disk format requires a major version and a documented
   migration tool. This is the promise that matters most for an
   event-sourced framework.

2. **Declarative surface** — the annotations (`#[db]`, `#[http]`,
   `#[permission]`, `#[lifecycle]`, `#[retention]`, `#[pinned]`,
   `#[relation]`, `#[server]`, `#[schema]`), the builder API
   (`LithairServer` / `LithairServerBuilder` public methods), the
   generated REST endpoint shapes, and the built-in operational
   endpoints (`/health`, `/ready`, `/info`, `/metrics`). Additive
   evolution only within 1.x; removals go through the
   [deprecation policy](../policy/deprecation.md).

3. **Rust API beyond the declarative surface** — engine internals
   (`Scc2Engine`, `EventStore`, …) were public mostly for testability. They
   were audited for 1.0 (G3): each item either joined the stable surface, moved
   behind `#[doc(hidden)]`, or got an explicit *unstable* marker — recorded in
   [`api-stability.md`](../reference/api-stability.md). `__private` is excluded
   from any promise.

Environment variables (`LT_*`) and the wire/replication protocol follow
surface 2 and the cluster gate below, respectively.

## Gates — what must be true before tagging v1.0

### G1 — Cluster: stabilize or formally scope out

Cluster mode (issue #104) is the largest open question. The 4 failing
multi-write BDD scenarios (#29 — leader connection drops) must be
diagnosed and fixed, with sustained-load proof, **or** v1.0 ships with
cluster explicitly excluded from the stability contract (feature-gated,
documented as preview, no wire-format promise). Both outcomes are
acceptable for 1.0; shipping an undiagnosed cluster path is not.

**RESOLVED (2026-06-12): production-stable within a documented operating
envelope.** The #29 failure mode was root-caused (bbfeb44 — stale shared
WAL replay) and fixed; the full `@real-cluster` BDD suite ran 3×
consecutive green, and a sustained-load run (170 200 writes, 11.3 min
endurance) showed zero drops, zero panics, zero replication divergence —
evidence posted on issue #104. The envelope (single-leader writes at a
measured ~210–240 ops/s ceiling, static lowest-ID election, fixed
membership) and its operating procedures are the contract:
[`docs/operations/cluster.md`](../operations/cluster.md). Raising the
ceiling is perf work (#126), not a 1.0 gate.

### G2 — Macro parser hardening

Three bugs of the same class shipped because the attribute parser
silently skips tokens it does not understand (#75 `validate`, the
`retention`/`pinned` helper-attribute miss, #122 `db(fk)`). Before 1.0,
unknown or unparsable tokens inside model attributes become a
**compile error**, so the next mistake fails the build instead of
silently dropping a constraint.

### G3 — API surface audit

The pass described in surface 3 above, recorded in a
[`docs/reference`](../reference/) table: every public item classified
stable / unstable / hidden. The audit also locks an MSRV policy
(currently: the pinned toolchain in
[`rust-toolchain.toml`](../../rust-toolchain.toml); 1.x will document
how far back it supports).

**RESOLVED (2026-06-18): API surface classified, MSRV policy locked.**
[`docs/reference/api-stability.md`](../reference/api-stability.md) tiers the
public surface into stable / unstable / hidden and records the MSRV policy
(minimum = the pinned toolchain, raised only in a minor with a CHANGELOG
note). The stable application surface is made executable by the
`lithair_core::prelude` (added in #142); the engine internals public only for
testability (`Scc2Engine`, `FileStorage`, `AsyncWriter`, the optimized
persistence path) are now `#[doc(hidden)]`. `EventStore` stays public and
classified *unstable* — the `lithair verify` CLI opens it — rather than
hidden. A prerequisite surfaced and was fixed first: the admin API planes
were not secure by default (#143), so they could not honestly be classified
*stable* until `with_data_admin()` auto-applied an auth guard. Tracked in #129.

### G4 — Published baselines

Reproducible benchmark scripts plus published results against at least
one conventional baseline (issue #108 benchmarks item). The point is
honest positioning ("when Lithair wins / loses"), not winning charts —
a 1.0 invites comparisons and must arrive with its own numbers.

**RESOLVED (2026-06-23): reproducible harness + published numbers vs a
baseline.** `benchmarks/run.sh` (`task bench:baselines`) drives the same
`tools/loadgen` harness against Lithair and an Axum+SQLite baseline
(`benchmarks/baseline-axum-sqlite`, file-backed so the write comparison is
durable-vs-durable), reporting CRUD throughput + p50/p95/p99.
[`docs/performance/baselines.md`](../performance/baselines.md) publishes the
methodology and an honest wins/loses: Lithair wins reads (~1.3–1.7 ms p50,
flat under load), loses write throughput ~30–60× (the single-leader durable
append, consistent with the documented ~210–240 ops/s envelope; raising it is
#130). The remaining matrix the issue lists (Actix+Postgres, memory-growth,
cold-start-replay, point-read, multi-run stddev) is named as deferred in the
doc and tracked in #126 — the harness makes each a small addition.

### G5 — Real-world soak

At least one application other than the maintainer's own runs a 1.0
release candidate in production through an upgrade cycle (0.x → RC →
RC+1) without data loss or unplanned downtime. The
[ops runbooks](../operations/) are the contract for that exercise: if
the soak needs steps the runbooks don't cover, the runbooks grow first.

**RESOLVED (2026-06-30): rc.1 soaked in production.** The showcase site
(`lithair-website`) runs `1.0.0-rc.1` in production with no data loss; the
upgrade path (rebuild + replay) and the secure-by-default admin / role-scoping
were exercised live. The original text asks for a *third-party* app; the
maintainer judged a real production deployment of the maintainer's own site
sufficient for 1.0 (a wider external soak continues in the open after release).
Three items surfaced and were triaged: two were not Lithair (a downstream
playground cookie example, a downstream Taskfile/VPS deploy issue); the one
Lithair item was a **scope decision, not a bug** — zero-downtime across a
*binary* change is now an explicitly documented limitation of the single-binary
model, not a v1.0 promise (content + frontend reload stay zero-restart). See
[upgrade.md → Downtime](../operations/upgrade.md#downtime-what-is-and-isnt-zero-restart).

### G6 — Deprecation machinery exercised

The [deprecation policy](../policy/deprecation.md) applied at least
once on a real API (deprecate in minor N, remove in N+2) so the
process is proven before it backs a promise.

**RESOLVED (2026-06-28): full deprecate → remove cycle proven.** The
`#[deprecated]` half was already in use (items marked since 0.2.0); the
never-demonstrated half — *removal* — is now done: `http::admin::AdminHandler`
and `dispatch_admin_route`, deprecated since 0.2.0 and used by nothing, were
removed (well past the remove-no-earlier-than-N+2 window), as a CHANGELOG
`Removed` entry referencing the original deprecation per the policy. Items still
load-bearing despite their 0.2.0 deprecation (`consensus::ConsensusConfig` /
`DeclarativeConsensus`, used by `DeclarativeHttpHandler`) are deliberately left
until a `with_raft_cluster` migration — the policy's point is a proven process,
not a forced break.

### G7 — Backup/restore proven, not just documented

The backup/restore/PITR runbook ([backup-restore.md](../operations/backup-restore.md))
exists, but no test proves the full cycle. Before 1.0 — and before any
real dataset (e.g. the showcase site's content) is trusted to the event
store — an automated end-to-end drill must back up, wipe, restore to
fresh state, and assert field-level identity plus a valid hash chain,
and a `lithair verify` command must let an operator check a restored
backup by hand. A documented backup that has never been restored is not
a 1.0 promise, it is a guess. Tracked in #133 (and #37 for the verify
CLI / import endpoint).

**RESOLVED (2026-06-16): backup/restore proven.** The end-to-end drill
(`lithair-core/tests/backup_restore_drill_test.rs`) backs up, wipes,
restores, and asserts field-level identity + valid hash chain + a
chain-continuing write after restore, in both JSON and binary log modes
plus the torn-tail case; `lithair verify <data-dir>` ships for offline
integrity checks (PR #136, #133). Proving it surfaced and fixed two
latent binary-mode format bugs (genesis event dropped on bincode replay;
binary log unreadable on reopen) — recorded for the v0.14 CHANGELOG under
on-disk-format. The logical-import endpoint remains in #37.

### G8 — Frontend lifecycle API (hot, no full restart)

Updating a frontend must not require restarting Lithair. A complete
admin API (`/_admin/frontend/*`) must let a deploy pipeline list the
configured frontends, inspect each one's config and a comparable
**version/fingerprint**, and reload a single vhost (or all) atomically
in memory — with zero impact on the data/event store or other vhosts.
The underlying reload machinery exists but is not wired to the
`LithairServer` builder path. This is what turns "redeploy = restart
everything" into "redeploy = one API call." Tracked in #134.

**RESOLVED (2026-06-16): `/_admin/frontend/*` shipped** (PR #138, #134).
List / inspect (config + cached `sha256:` version + manifest) / reload —
per-vhost and all, covering both the path-prefix and vhost storage paths.
Reloads are atomic (build new set, swap under the write lock), node-local
(correctly exempt from Raft write-redirection so a follower reloads its
own assets), and the version is O(1) cached, recomputed only at
load/reload. An integration test proves a single-vhost reload changes
that vhost's content + version while the other's stays put, with no
server restart. Combined with G7, an installed Lithair supports
content-in-backend updates and frontend updates with no downtime except
binary changes.

These two gates (G7, G8) were added after the 2026-06-16 operational
review: the original gates were weighted toward code cleanliness (G2,
G3) and under-weighted the *lifecycle of an installed product* — can
its operator update content, update the frontend, and trust backups
without downtime. Those are the questions that actually decide whether
1.0 is safe to depend on.

## Already behind us

For calibration, the production-readiness work completed during 0.12–0.13:
operational runbooks and deployment artifacts (#106), observability —
tracing, correlation IDs, opt-in OTLP export (#107), graceful shutdown
(#112), production-realistic BDD coverage that found and fixed real bugs
(#105 → #121, #122), and the retention/tiering system (#96, #97, #98).

## Out of scope for 1.0

Tiered cold-query indexing (#73 remainder), native mutation hooks (#70),
and per-vhost models/RBAC (#32) are valuable but additive — they can
land in any 1.x without touching the contract.
